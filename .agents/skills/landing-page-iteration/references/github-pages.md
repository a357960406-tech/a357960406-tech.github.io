# GitHub Pages 发布与线上验证

仅在用户要求提交、上传或发布的对应范围内使用。分析参考、制作预览、创建 Skill 不自动授权发布。

## 发布前

检查仓库、分支、变更与远程，提交只包含预期文件。排除凭据、临时截图、依赖目录和本机配置；保留用户未提交的工作。

沿用现有构建方式：静态 HTML 无需额外构建，有构建工具则发布实际输出。核对引用文件、字体、图片、下载路径与部署目录。

用户站点仓库通常为 `<用户名>.github.io`，项目站点有仓库路径前缀。通过当前远程与用户要求确定目标，不沿用本次账号作为新项目默认值。

## 保持一种主要发布来源

选择分支目录或 GitHub Actions 上传产物，避免两套流程发布不同根目录并相互覆盖。

- Actions：核对触发分支、Pages 权限、上传路径、部署结果及网站 URL。
- 分支：核对 Pages 设置的分支、目录、入口与所需的 .nojekyll。
- 根入口跳转时，确认目标子目录在产物中，不能只检查根入口 HTTP 200。
- 相对路径或配置后的 base 必须适配实际项目网址。

## 上传和认证

优先沿用可用的 Git 或 GitHub 连接器。浏览器、CLI 与连接器认证可能互相独立，一个浏览器登录不代表另一工具有权限。

连接无响应时先检查已产生的结果，再换可用通道；不反复建仓库或在错误浏览器要求登录。避免无限期等待。需要用户操作时，说明通道、具体卡点和最短步骤。

连接器逐文件上传时：

- 二进制少量并发，保存成功对象的 SHA，仅重试失败项；不要大量输出 base64 或拼巨大命令。
- 核对完整清单后创建 tree 和 commit。更新主分支时使用预期旧 HEAD，遇并发变化先检查，不强推覆盖。
- 基于远程历史保留已有内容。API 提交与本地历史不同，先确认文件树一致并保留本地快照，再同步跟踪分支。
- 上传、更新分支、部署是不同状态。API 上传不能描述成实际执行了 git push。

## 完成条件

1. 有对应提交，或明确说明未提交内容。
2. 远程分支上能确认本次版本。
3. 发布流程明确成功，不只是已触发。
4. 正式网址及跳转后的真实页面可访问且为最新版本。
5. 浏览器确认关键样式、图片与本轮交互；资源可能晚于 DOM 加载，等样式生效后再判断布局。

公开 Pages API 的 404 不足以单独证明未启用：接口可能要求认证。结合已授权接口、发布记录和实际网址判断。

部署成功但未更新时，先核对缓存、入口、产物目录和多流程覆盖。交付真实网站与仓库链接；未经验证的地址标为预计。
